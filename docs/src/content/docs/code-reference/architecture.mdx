## Visão geral

O WinUtil é um utilitário Windows baseado em PowerShell com uma interface gráfica WPF (Windows Presentation Foundation). Este documento explica a arquitetura, a estrutura do código e como os diferentes componentes trabalham juntos.

## Arquitetura de alto nível

```
│                    Winutil GUI                      │
│              (WPF XAML Interface)                   │
```

### Componentes principais

#### 1. Compile.ps1
**Propósito**: Combina todos os arquivos de script separados em um único `winutil.ps1` para distribuição.

**Processo**:
1. Lê todos os arquivos de função de `/functions/`
2. Inclui os arquivos JSON de configuração
3. Incorpora a definição da interface XAML
4. Combina tudo em um único script
5. Gera o `winutil.ps1`

**Por quê**: Facilita a distribuição (arquivo único) e melhora o tempo de carregamento.

#### 2. scripts/main.ps1
**Propósito**: Ponto de entrada que gerencia a execução.

**Responsabilidades**:
- Carregar as configurações
- Executar os caminhos headless `-Preset` e `-Config`
- Iniciar a interface em um runspace STA dedicado e aguardar
- Relatar qualquer falha da thread da interface e então limpar

A interface em si fica em `Start-WinUtilUserInterface`, não aqui. Veja [Modelo de threads](#modelo-de-threads).

`Update-WinUtilWindowInsets` mantém o conteúdo maximizado dentro da área útil do monitor atual. Ele mede os limites nativos da janela, converte a sobra para unidades WPF e atualiza a grade principal após mudanças de tamanho, posição, DPI ou área útil. Restaurar a janela remove o recuo.

#### 3. functions/public/
**Propósito**: Funções voltadas ao usuário que implementam os recursos principais.

**Funções principais**:
- `Initialize-WPFUI.ps1`: Configura a interface gráfica
- `Invoke-WPFTweak*`: Aplica ajustes do sistema
- `Invoke-WPFFeature*`: Habilita recursos do Windows
- `Install-WinUtilProgram*`: Instala aplicativos

**Convenção de nomes**: As funções começam com `WPF` ou `Winutil` para serem carregadas no runspace.

#### 4. functions/private/
**Propósito**: Funções auxiliares internas, não chamadas diretamente pelos usuários.

**Funções principais**:
- `Get-WinUtilVariables.ps1`: Obtém referências a elementos da interface
- `Install-WinUtilWinget.ps1`: Garante que o WinGet esteja instalado
- `Get-WinUtilCheckBoxes.ps1`: Obtém o estado das caixas de seleção
- `Invoke-WinUtilCurrentSystem.ps1`: Obtém informações do sistema

#### 5. config/*.json
**Propósito**: Definir aplicativos, ajustes e recursos disponíveis de forma declarativa.

**Arquivos**:
- `applications.json`: Definições de aplicativos com IDs de WinGet/Choco
- `tweaks.json`: Ajustes de registro e suas ações de desfazer
- `feature.json`: Recursos do Windows que podem ser habilitados/desabilitados
- `preset.json`: Combinações de ajustes predefinidas
- `dns.json`: Configurações de provedores de DNS

#### 6. xaml/inputXML.xaml
**Propósito**: Layout e design da interface WPF.

**Estrutura**:
- Botões com manipuladores de eventos
- TextBoxes para entrada
- CheckBoxes para opções
- ListBoxes para seleções

## Arquitetura do Criador do Win11

O **Criador do Win11** é um subsistema especializado dentro do Winutil que cria ISOs personalizadas do Windows 11. Ele funciona independentemente do sistema principal de instalação de pacotes e de ajustes.

### Componentes do Criador do Win11

**Funções centrais** (`functions/private/`):
- `Invoke-WinUtilISO.ps1`: Orquestrador principal, contendo o fluxo da ISO e funções auxiliares
  - `Invoke-WinUtilISOBrowse`: Diálogo de seleção do arquivo ISO
  - `Invoke-WinUtilISOMountAndVerify`: Valida e monta a ISO, verificando se é uma ISO oficial do Windows 11
  - `Invoke-WinUtilISOModify`: Inicia a modificação em um runspace em segundo plano
  - `Invoke-WinUtilISOExport`: Monta a ISO inicializável via `oscdimg.exe`
  - `Invoke-WinUtilISOCheckExistingWork`: Recupera sessões de trabalho incompletas
  - `Invoke-WinUtilISOCleanAndReset`: Limpa diretórios temporários e redefine a interface
  - `Write-WinUtilISOLog`: Publica mensagens de log na caixa de status e no log da sessão
  - `Set-WinUtilISOStep`: Controla o estado de navegação do assistente
  - `Get-WinUtilEditionIdFromName`: Mapeia nomes de exibição de edição para IDs de edição da instalação
  - `Invoke-WinUtilRobocopy`: Copia arquivos com verificação de código de saída
  - `Find-WinUtilOscdimg` / `Get-WinUtilOscdimgPath`: Localiza ou instala o `oscdimg.exe`

- `Invoke-WinUtilISOUSB.ps1`: Detecção e formatação de pendrives
  - `Invoke-WinUtilISORefreshUSBDrives`: Enumera os pendrives
  - `Get-WinUtilFreeDriveLetter`: Encontra letras de unidade disponíveis
  - `Invoke-WinUtilISOWriteUSB`: Formata o pendrive como GPT/FAT32, divide o WIM se necessário e copia os arquivos

- `Invoke-WinUtilISOScript.ps1`: Prepara a mídia de instalação e as personalizações
  - Prepara a remoção de AppX (19 pacotes de bloatware) no `autounattend.xml` para o primeiro logon
  - Aplica mais de 50 ajustes de registro durante a Instalação do Windows e o primeiro logon; remove tarefas agendadas no primeiro logon
  - Dispara a desinstalação do OneDrive no primeiro logon
  - Prepara scripts de instalação de reserva em `sources\$OEM$\$$\Setup\Scripts\`
  - Fixa a edição selecionada no `autounattend.xml` e grava `sources\ei.cfg`
  - Injeta drivers elegíveis do sistema atual nas imagens WIM quando habilitado (a montagem do WIM é usada apenas para o serviço de drivers)

### Fluxo de dados do Criador do Win11

```
User selects official Windows 11 ISO
    ↓
Invoke-WinUtilISOBrowse → OpenFileDialog, validates file size
    ↓
Invoke-WinUtilISOMountAndVerify
    ├─ Mount ISO via Mount-DiskImage
    ├─ Verify install.wim or install.esd exists
    ├─ Check for "Windows 11" in image metadata
    ├─ Extract available editions (Home, Pro, Enterprise, etc.)
    └─ Store ISO path, drive letter, WIM path, image info in $sync
    ↓
User optionally enables the Driver Injection checkbox
    ↓
Invoke-WinUtilISOModify (runs in background runspace)
    ├─ Create work directory: ~WinUtil_Win11ISO_[timestamp]
    ├─ Copy ISO contents to disk via robocopy (~5-6 GB)
    ├─ Invoke-WinUtilISOScript:
    │   ├─ Generate autounattend.xml with Windows PE and specialize safeguards
    │   ├─ Add first-logon script (19 AppX removals, registry tweaks, OneDrive uninstall)
    │   ├─ Pin selected edition index in autounattend.xml (/IMAGE/INDEX)
    │   ├─ Stage setup script fallbacks to sources\$OEM$\$$\Setup\Scripts\
    │   ├─ Write sources\ei.cfg and remove stale sources\PID.txt
    │   └─ If driver injection enabled:
    │       ├─ Require install.wim; install.esd cannot accept driver injection
    │       ├─ Export current system drivers via DISM
    │       ├─ Exclude stale duplicate packages
    │       ├─ Inject storage drivers into boot.wim index 2 and eligible drivers into install.wim
    │       └─ Validate WIM metadata before and after injection
    ├─ Dismount source ISO
    └─ Report completion, enable export options
    ↓
Invoke-WinUtilISOExport (user chooses output)
    ├─ Option 1: Save as ISO
    │   ├─ Build bootable ISO via oscdimg.exe (BIOS/UEFI dual-boot)
    │   └─ Output: Win11_Modified_[date].iso (close to the source ISO size)
    │
    └─ Option 2: Write to USB
        ├─ Format USB as GPT
        ├─ Create single FAT32 partition (capped at 32 GB)
        ├─ Split install.wim into .swm files if > 3.8 GB
        ├─ Reject install.esd files of 4 GB or more
        ├─ Copy files via robocopy
        └─ Output: Bootable USB (minimum 8 GB)
    ↓
Invoke-WinUtilISOCleanAndReset (optional)
    ├─ Dismount any open WIM mounts with discard
    ├─ Delete temp working directory (~10-15 GB)
    └─ Reset UI to initial state
```

### Validação e segurança do Criador do Win11

**Validação da ISO**:
- Aceita apenas ISOs oficiais do Windows 11 da Microsoft
- Valida a presença de install.wim ou install.esd
- Verifica nos metadados da imagem a string "Windows 11"
- Rejeita ISOs personalizadas, modificadas ou que não sejam do Windows 11

**Validação de metadados do WIM**:
- Durante a injeção de drivers, `Assert-WinUtilISOWimMetadata` valida campos críticos (`Languages`, `Installation`, `Edition`, `ProductSuite`, `ProductType`) antes e depois do serviço de WIM
- A injeção de drivers para antes da exportação se os metadados necessários estiverem ausentes ou mudarem
- Sem injeção de drivers, o WinUtil preserva a imagem de instalação original e ignora a validação de metadados do WIM

**Fixação de edição e reserva da instalação**:
- Grava `sources\ei.cfg` e remove `sources\PID.txt` para que a instalação não use chaves de produto OEM incompatíveis
- Fixa o índice da edição selecionada no `autounattend.xml` (`/IMAGE/INDEX`)
- Prepara scripts de instalação de reserva em `sources\$OEM$\$$\Setup\Scripts\` com `UseConfigurationSet` habilitado

**Recuperação de sessão de trabalho**:
- Detecta automaticamente trabalho incompleto de sessões anteriores
- Permite retomar a etapa de exportação sem repetir a seleção e a modificação
- Evita modificações redundantes

**Segurança da modificação**:
- Windows PE e a fase de especialização definem a ignorância de hardware e as proteções da instalação; `WinUtil-PostInstall.ps1` aplica mudanças adicionais no registro no primeiro logon
- A ISO original nunca é modificada; apenas a cópia de trabalho
- Registrado no arquivo de sessão compartilhado `%LocalAppData%\winutil\logs\winutil_<timestamp>.log` e no painel de status ao vivo da interface, para que o log sobreviva à limpeza
- O DISM cuida da desmontagem da imagem com limpeza automática e descarte em caso de erro

### Ajustes de registro do Criador do Win11

A função `Invoke-WinUtilISOScript` aplica **mais de 50 ajustes de registro** durante a instalação e o primeiro logon:

**Ignorância de hardware**:
- Ignorar a verificação de TPM 2.0
- Ignorar a exigência de Secure Boot
- Ignorar a compatibilidade de CPU
- Ignorar a exigência de RAM
- Ignorar a verificação de armazenamento

**Privacidade e telemetria**:
- Desabilitar ID de publicidade
- Desabilitar experiências personalizadas
- Desabilitar personalização de entrada
- Desabilitar privacidade online de fala
- Desabilitar sugestões de conteúdo na nuvem
- Desabilitar assinaturas de sugestão de apps
- Remover CEIP, Appraiser, WaaSMedic etc.

**OOBE e instalação**:
- Habilitar configuração com conta local
- Ignorar a exigência de conta da Microsoft
- Modo escuro por padrão
- Barra de tarefas e Menu Iniciar vazios

**Instalações pós-configuração**:
- Impedir a instalação automática do DevHome
- Impedir a instalação do novo app Outlook Mail
- Impedir a instalação automática do Teams

**Recursos do sistema**:
- Desabilitar BitLocker e criptografia de dispositivo
- Desabilitar o ícone do Chat na barra de tarefas
- Desabilitar o backup de pastas do OneDrive
- Desabilitar o Copilot
- Desabilitar o Windows Update durante a OOBE (reabilitado no primeiro login)

### Recurso de injeção de drivers

**Melhoria opcional**: quando habilitada, exporta todos os drivers do sistema em execução e os injeta em:
- `install.wim` (imagem principal do sistema operacional), excluindo duplicados obsoletos
- `boot.wim` índice 2 (ambiente PE da Instalação do Windows), apenas controladores de armazenamento (`SCSIAdapter` / `HDC`)

**Caso de uso**: Permite instalação offline em sistemas com drivers ausentes.

### Requisitos de espaço em disco

- **Diretório de trabalho temporário**: ~10-15 GB
- **ISO original**: 4-6 GB
- **ISO modificada**: próxima do tamanho da ISO de origem
- **Total necessário**: ~25 GB para operar com segurança

## Formato dos arquivos de configuração

### Estrutura do applications.json

```json title="config/applications.json"
{
  "WPFInstall<AppName>": {
    "category": "Browsers",
    "choco": "googlechrome",
    "content": "Google Chrome",
    "description": "Google Chrome browser",
    "link": "https://chrome.google.com",
    "winget": "Google.Chrome"
  }
}
```

**Campos**:
- `category`: Qual seção na aba Instalar
- `content`: Nome exibido na interface
- `description`: Texto da dica/descrição
- `winget`: ID do pacote no WinGet
- `choco`: Nome do pacote no Chocolatey
- `link`: Site oficial

### Estrutura do tweaks.json

```json title="config/tweaks.json"
{
  "WPFTweaksTelemetry": {
    "Content": "Disable Telemetry",
    "Description": "Disables Microsoft Telemetry",
    "category": "Essential Tweaks",
    "panel": "1",
    "registry": [
      {
        "Path": "HKLM:\\SOFTWARE\\Policies\\Microsoft\\Windows\\DataCollection",
        "Name": "AllowTelemetry",
        "Type": "DWord",
        "Value": "0",
        "OriginalValue": "1"
      }
    ]
  }
}
```

**Campos**:
- `Content`: Nome exibido
- `Description`: O que faz
- `category`: Essential/Advanced/Customize
- `registry`: Mudanças de registro a fazer
- `registry[].Values`: Valores por estado de uma combobox baseada em registro
- `registry[].DefaultValue`: Valor efetivo quando a entrada de registro está ausente
- `service`: Serviços a alterar
- `OriginalValue/State`: Para a funcionalidade de desfazer

## Modelo de threads

O WinUtil roda em três tipos de thread, e cada uma tem uma função:

| Thread | Runspace | Responsabilidade |
| --- | --- | --- |
| Principal | Aquele em que o script foi iniciado | Iniciar a interface, aguardá-la, expor os erros dela, limpar |
| Interface | `$sync.UIRunspace`, um runspace STA dedicado | Ser dono da janela. Desenhar e despachar, nada além |
| Trabalhadores | `$sync.runspace`, um pool compartilhado | Rodar tudo que é longo: instalações, ajustes, recursos, AppX, Criador do Win11 |

As três são criadas a partir do mesmo ponto de partida, `New-WinUtilSessionState`, que carrega o
`$sync`, as variáveis globais do script compilado e todas as funções do WinUtil. É isso que permite que qualquer
thread chame qualquer auxiliar sem que o chamador injete definições de função.

```powershell
# main.ps1 - the interface gets its own thread
$sync.UIRunspace = [runspacefactory]::CreateRunspace($Host, (New-WinUtilSessionState))
$sync.UIRunspace.ApartmentState = "STA"
$sync.UIRunspace.Open()

$uiShell = [powershell]::Create()
$uiShell.Runspace = $sync.UIRunspace
[void]$uiShell.AddScript({ Start-WinUtilUserInterface })
$uiHandle = $uiShell.BeginInvoke()
while (-not $uiHandle.AsyncWaitHandle.WaitOne(250)) {
    Receive-WinUtilStreamOutput -PowerShell $uiShell -Component "UI"
}
```

**Por quê**: a janela nunca bloqueia por causa de trabalho, e uma falha na thread da interface é
relatada em vez de desaparecer.

## Trabalho de longa duração

Toda ação longa passa por `Start-WinUtilJob`, que centraliza tudo o que uma operação em execução
precisa: recusar o início enquanto outro job roda, a flag de ocupado (`$sync.ActiveJob`), a barra
de progresso e o item da barra de tarefas, o banner do console em caixa, uma linha de início/fim/falha no log e
a restauração da interface em um `finally`, aconteça o que acontecer.

`Invoke-WPFButton` decide o que conta como ação longa. Tudo o que muda o sistema ganha um
job; tudo o que só muda o que a interface está mostrando roda na thread da interface.
Essa classificação única é o motivo de nenhum fluxo de trabalho organizar o próprio progresso, banner ou estado de ocupado.

**Fila**: uma ação iniciada pelo usuário passa `-QueueIfBusy`, então, enquanto outro job roda, ela espera
em `$sync.JobQueue` em vez de ser recusada. O teste de ocupado e a entrada na fila acontecem sob um único
bloqueio `$sync.SyncRoot`. Quando um job termina, com sucesso ou não, `Clear-WinUtilActiveJob` publica
`Start-WinUtilNextQueuedJob` na thread da interface, que inicia a entrada mais antiga. A fila
compara apenas sua última entrada ao suprimir pedidos idênticos, preservando ações repetidas depois de trabalho
intercalado. Ela guarda os parâmetros do job como estavam no momento do clique, então mudanças posteriores na seleção não a alteram.
O botão de relógio no cabeçalho lista os jobs em execução e na fila e permite ao usuário reordenar
ou cancelar os que estão na fila. As transferências pausam enquanto a pergunta de fechamento está aberta, então a resposta
não pode afetar um job diferente na fila. Fechar a janela descarta tudo o que ainda estiver na fila. Os jobs de ISO e pendrive
não passam a chave e continuam recusando.

```powershell
Start-WinUtilJob -Name "Features" -Description "Installing Windows Features" -Parameters @{
    Features = @($sync.selectedFeatures)
} -ScriptBlock {
    param($Features)

    $total = @($Features).Count
    $completed = 0
    foreach ($feature in $Features) {
        $completed++
        Step-WinUtilJob -Status "Installing $feature ($completed/$total)" -Percent ([int](($completed / $total) * 100))
        Invoke-WinUtilFeatureInstall $feature
    }
}
```

O corpo só precisa fazer o trabalho e chamar `Step-WinUtilJob`. Tudo o que ele lançar é
capturado, registrado e mostrado na barra de tarefas como falha.

**Valores, não closures**: o corpo é reconstruído dentro do worker a partir do seu texto, então ele recebe
o que precisa por `-Parameters`, em vez de capturar as variáveis do chamador.

## Tratamento de eventos WPF

Os eventos são conectados pelos nomes dos elementos XAML:

```powershell
# Get all named elements
$sync.keys | ForEach-Object {
```

## Integração com gerenciadores de pacotes

### Integração com o WinGet

```powershell
# Check if installed
if (!(Get-Command winget -ErrorAction SilentlyContinue)) {
    Install-WinUtilWinget
}

# Install package
winget install --id $app.winget --silent --accept-source-agreements
```

### Integração com o Chocolatey

```powershell
# Check if installed
if (!(Get-Command choco -ErrorAction SilentlyContinue)) {
    Install-WinUtilChoco
}

# Install package
choco install $app.choco -y
```

## Tratamento de erros e logging

O corpo de um job não precisa do próprio tratamento de erro. `Start-WinUtilJob` captura tudo o que o corpo
lança, registra no log e marca a execução como falha na barra de tarefas, então uma falha nunca deixa a
interface presa em estado ocupado. Só capture dentro de um corpo quando você tiver algo específico a fazer antes,
como limpar uma imagem montada, e então relance o erro.

```powershell
Write-WinUtilLog -Level "ERROR" -Component "Install" -Message "winget install failed: $($_.Exception.Message)"
```

Toda thread escreve no mesmo arquivo de sessão `%LocalAppData%\winutil\logs\winutil_<timestamp>.log`
por meio de um único escritor compartilhado. `Start-WinUtilJob` registra os avisos, erros e a saída de
`Write-Host` de um job, e a thread principal registra os da thread da interface enquanto a janela está aberta. Banners e
progresso passam por `Write-WinUtilHost` em vez de `Write-Host`, para ficarem fora do log.

## Carregamento de configurações

Na inicialização, o Winutil carrega todas as configurações:

```powershell
# Load JSON configs
$sync.configs = @{}
$sync.configs.applications = Get-Content "config/applications.json" | ConvertFrom-Json
$sync.configs.tweaks = Get-Content "config/tweaks.json" | ConvertFrom-Json
$sync.configs.features = Get-Content "config/feature.json" | ConvertFrom-Json
```

**Sync Hash**: A hashtable `$sync` compartilha estado entre runspaces.

## Padrão de atualização da interface

Controles só podem ser acessados pela thread dona da janela, então o trabalho em segundo plano chega
a eles por `Invoke-WPFUIThread`:

```powershell
Invoke-WPFUIThread -Parameters @{ Count = $installed.Count } -ScriptBlock {
    param($Count)
    $sync.WPFselectedAppsButton.Content = "Selected Apps: $Count"
}
```

Adicione `-Async` para publicar a atualização em vez de esperar por ela. `Step-WinUtilJob` e o
log de status do Criador do Win11 usam isso para que uma atualização por item nunca trave o worker.

**Valores, não closures**: o corpo é reconstruído dentro do runspace da interface, então ele recebe o que
precisa por `-Parameters`. Entregar um scriptblock de um worker manteria o estado de sessão desse
worker, o que perde as variáveis do chamador em uma publicação assíncrona e custa cerca de
vinte vezes mais por comando — o suficiente para transformar uma atualização de caixa de seleção em um travamento visível.

## Adicionando novos recursos

### Adicionando um novo aplicativo

1. Edite `config/applications.json`:
```json title="config/applications.json"
{
  "NewApp": {
    "category": "Utilities",
    "content": "New App",
    "description": "Description of new app",
    "winget": "Publisher.AppName",
    "choco": "appname"
  }
}
```

2. Adicione o ícone como `config/icons/<key>.png`, com o nome da chave em `applications.json` (`NewApp` acima; o `Compile.ps1` adiciona o prefixo `WPFInstall`). Qualquer imagem quadrada serve: `.\tools\New-WinUtilIcon.ps1 -Key NewApp -Path logo.png` a redimensiona para o tamanho 48x48 que os testes esperam. Sem arquivo de ícone, o app usa o favicon do site como alternativa.
3. Recompile: `.\Compile.ps1`
4. O app aparece automaticamente na aba Instalar

### Adicionando um novo ajuste

1. Edite `config/tweaks.json`:
```json title="config/tweaks.json"
{
  "WPFTweaksNewTweak": {
    "Content": "New Tweak",
    "Description": "What it does",
    "category": "Essential Tweaks",
    "registry": [
      {
        "Path": "HKLM:\\Path\\To\\Key",
        "Name": "ValueName",
        "Type": "DWord",
        "Value": "1",
        "OriginalValue": "0"
      }
    ]
  }
}
```

2. Recompile: `.\Compile.ps1`
3. O ajuste aparece na aba Ajustes

### Adicionando uma nova função

1. Crie o arquivo em `functions/public/` ou `functions/private/`:
```powershell
# functions/public/Invoke-WPFNewFeature.ps1
function Invoke-WPFNewFeature {
    <#
    .SYNOPSIS
    Does something new
    #>
    # Implementation
}
```

2. O nome do arquivo deve incluir "WPF" ou "Winutil" para ser carregado
3. Recompile: `.\Compile.ps1`

### Testes automatizados

```powershell
Install-Module -Name Pester -RequiredVersion 5.8.0 -Scope CurrentUser -Force -SkipPublisherCheck
Import-Module Pester -RequiredVersion 5.8.0 -Force
Invoke-Pester -Path 'pester/*.Tests.ps1' -Output Detailed -CI
```

## Considerações de desempenho

**Estratégias de otimização**:
